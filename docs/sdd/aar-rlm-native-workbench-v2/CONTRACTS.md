# AR-RW Executable Contract Profile

**Normative status:** required by `README.md`; implementation MUST NOT choose different public semantics without revising this package and repeating independent review.

**Generated contract manifest:** `contracts/contract-manifest.json`

## 1. Precedence

For AR-RW successor behavior, the order is:

1. frozen v1 source schemas and fixtures for compatibility;
2. generated JSON schemas named by `contracts/contract-manifest.json`;
3. this file's cross-field and canonicalization rules;
4. `LIFECYCLE.md` for transition and atomicity semantics;
5. explanatory sketches in `README.md`.

A contradiction is a specification failure. Implementation does not resolve it by choosing one silently.

## 2. JSON and digest profile

`aar.json-schema-profile.v1` means:

- dialect: JSON Schema Draft 2020-12;
- raw JSON parser MUST reject duplicate object keys, non-finite numbers, trailing data, invalid UTF-8 and lone surrogate code points;
- no input coercion;
- `format` is not validation authority and is forbidden in admitted user schemas;
- admitted keywords are exactly `$schema`, `$defs`, `$ref`, `type`, `properties`, `required`, `additionalProperties`, `items`, `minItems`, `maxItems`, `minLength`, `maxLength`, `minimum`, `maximum`, `pattern`, `enum`, `const`, `oneOf`, `allOf`, `if`, `then`, `else`, `not`, `minProperties`, `maxProperties`, `propertyNames`, `title`, and `description`;
- `$ref` targets are local `#/$defs/...` JSON Pointers or package-local contract files listed in the manifest;
- remote schemes, absolute filesystem references, `$dynamicRef`, `$recursiveRef`, anchors, external `$id`, `unevaluatedProperties`, and vocabulary extensions are rejected;
- schema size: at most 65,536 canonical bytes;
- schema object depth: at most 32;
- schema nodes: at most 4,096;
- instance depth: at most 64;
- instance bytes: bounded by the enclosing contract and never above 1,048,576;
- regex patterns use the portable linear profile implemented by `portable_regex.py`: printable ASCII literals, positive ASCII character classes, an optional leading `^`, and at most one quantified atom in the entire pattern using only `?` or bounded `{m}` / `{m,n}` repetition with bounds at most 64; trailing `$` is forbidden because Python may match before a final newline while ECMAScript does not; only true regex syntax characters may be escaped, so ECMAScript-Unicode-invalid identity escapes such as `\-` are forbidden; groups, alternation, dot, negated classes, `*`, `+`, open-ended repetition, multiple quantified atoms, engine-specific escapes, backreferences, lookaround, inline flags and possessive/atomic constructs are rejected;
- caller-selected patterns are preflighted by `portable_regex.py` before Draft 2020-12 meta-validation, because a meta-validator may compile `pattern` with its host engine while checking schema syntax;
- this `pattern` profile is a prefix/search filter, not a whole-string security boundary; exact whole-string values use `const` or `enum`, and other full-value constraints use structural schema keywords rather than a nonportable end anchor;
- validation is fail-closed and reports no coerced successor value.

Canonical bytes use the existing AAR canonical JSON profile: UTF-8, object keys sorted lexicographically, no insignificant whitespace, and the current `canonical_json_bytes` scalar encoding. Digests are `sha256:` plus lowercase hexadecimal over those bytes. The generator and implementation MUST include cross-validator fixtures and prove equality with two independent Draft 2020-12 validators before admitting planner directives or terminal outputs.

## 5. Admission authority

### 5.1 Context

`McpRlmWorkbenchMutationContext` is separate from `McpRlmMutationContext` v1. It carries:

- principal and session;
- runtime generation and capability digest;
- request identity and payload-bound idempotency key;
- cumulative absolute deadline;
- sorted unique host-issued grant IDs;
- host maxima for wall time, model requests/tokens, child operations and artifact bytes.

It permits at most 900,000 ms because the operation can enter lease-free caller waits. It does not relax the v1 60,000 ms reference-host context.

### 5.2 Effective budgets

The job requests budgets; the context and grants authorize maxima. Admission succeeds only when every requested budget is less than or equal to every applicable host/grant/route maximum and the absolute deadline can cover the requested wall time. A mismatch fails before an operation or workspace is created. Silent capping is forbidden.

The cumulative deadline is `min(context.deadline_unix_ms, intent_persisted.at_unix_ms + spec.budgets.total_wall_time_ms)`. The `intent_persisted` timestamp is the first immutable public operation event and is written with the outer operation's `created_at_unix_ms`. A caller-work host therefore reconstructs the exact deadline from public operation events plus its original request bytes; service-local observation time and private database reads are not authority.

Cumulative usage is charged across attempts, successors, restarts, correction planner calls and failed cells. An idempotent replay of a certain receipt does not charge physical usage twice.

### 5.3 Caller-delegated start rule

When `execution_mode=caller_delegated`, `start_only` MUST be true. A blocking call cannot require the same caller to service work that has not yet been returned. A host-native driver may hide polling but it uses the same durable ticket protocol.

`start_only=false` is permitted only for `service_managed` with an admitted configured backend and independently owned lease keeper.

## 6. Route binding

The model policy embeds the exact frozen `aar.model-route.v1` `ModelRouteBinding`, including:

- profile ID;
- catalog and profile digests;
- provider driver, provider and model;
- reasoning effort;
- maximum output tokens;
- fallback policy;
- cache policy.

There is no parallel free-form fallback list. Admission recomputes the profile digest and requires exact membership in the current catalog. Route, effort, fallback, cache and output-token drift fail before physical dispatch. Every model observation binds the requested route receipt and usage receipt digests.

## 7. Broker contract registry

The registry key is `(method, contract_id, request_schema_digest, response_schema_digest)`. V1 rows remain present and unchanged. V2 rows are additive:

| Method | Contract ID | Facade operation |
|---|---|---|
| `model.request` | `aar.broker-contract.model-request.v2` | `aar.model.request()` |
| `subagent.submit` | `aar.broker-contract.subagent-submit.v2` | `aar.agents.submit()` |
| `subagent.result` | `aar.broker-contract.subagent-result.v2` | `aar.agents.await_result()` |
| `evidence.query` | `aar.broker-contract.evidence-query.v2` | `aar.evidence.query()` |
| `effect.propose` | `aar.broker-contract.effect-propose.v2` | `aar.effects.propose()` |

There is no `subagent.status.v2` or `subagent.await` broker method. `await_result()` is a Python convenience over `subagent.result.v2`. It may produce a caller ticket and durable wait.

A v2 catalog is admitted only when method names are unique, contract IDs are unique, the ordered row set is exact, and every row's request/response digest equals the published schema definition. Object-map coercion that could hide duplicate contradictory rows is forbidden.

One canonical v2 request traverses worker frame, caller/local dispatch, authorization, persistence and receipt. Converting to v1 or silently selecting a different row is forbidden.

## 8. Logical call identity

Every durable external call has one discriminated owner:

- planner owner: `initial`, `correction`, `recovery` or `finalizer`, plus step index;
- cell owner: cell execution ID plus broker-call ordinal.

Ticket identity is derived from operation, suspension revision, logical owner, method contract ID and request digest. Root planner calls do not invent a cell ID.

Subagent acceptance and subagent result are separate durable observations. The accepted child execution ID becomes the identity for later `subagent.result.v2`. Parent success is forbidden while a required child is live. Detached children are excluded from v1; `required` is therefore constant true.

## 10. Caller work API rules

The complete automaton is defined in `LIFECYCLE.md`. Contract rules include:

- claim creates a `send_reserved` state and binds claimant principal/session, adapter identity/generation, claim ID/fence, claim expiry and physical-attempt idempotency identity;
- `cancelled_before_send` is a terminal certain-no-send settlement reachable only from `pending | send_reserved`; it requires a local settlement receipt and forbids every send-evidence field;
- no physical send is legal before `aar_broker_work_mark_send_started` commits `send_started` together with the exact `sent_request_digest` after validating the current operation control/cancellation revision, suspension/ticket revision, cumulative deadline, claim expiry and claim fence in one transaction;
- an expired `send_reserved` claim is safe to reclaim because physical sends MUST be zero and all sent-evidence fields remain null;
- `send_started` is the conservative may-have-sent point, not proof that a syscall reached the provider or child;
- `sent_at_unix_ms` and `provider_or_child_request_id` are populated only when the host observes them; their absence after `send_started` remains indeterminate, while their presence is copied into candidate and settled receipts;
- commit appends a digest-bound candidate observation and the current coordinator settles it;
- `settled_success`, `settled_failure`, `cancelled_before_send`, and `cancelled_certain` require `settled_receipt_digest` plus `settled_at_unix_ms`; nonterminal and quarantined tickets expose both fields as null;
- stale or late callbacks may append matching candidate receipts but cannot mutate authoritative state directly;
- conflicting receipts quarantine;
- lookup/cancel capability is bound before send;
- all mutations are revision, digest, claimant and idempotency fenced.

Same key plus same payload returns the prior result. Same key plus changed payload is an idempotency conflict. Wrong principal, adapter generation, control/cancellation/suspension/ticket revision, claim fence, physical attempt, request digest, ticket digest, deadline or claim expiry fails without mutation.

### 10.1 Worker-frame authority

`WorkspaceBrokerFrame` is a closed `oneOf` over exact `(kind, direction, committed, payload)` variants. `stdout`, `stderr`, `rich_display`, `progress`, `broker_intent`, `artifact_stage_intent`, `completion_intent`, `execute_result`, `rebind_ack`, and `worker_protocol_error` are worker-to-supervisor proposals and have `committed=false`. `execute_request`, `broker_receipt`, `broker_suspend`, `rebind_prepare`, `rebind_commit`, `rebind_abort`, `cancel`, and `supervisor_protocol_error` are supervisor-to-worker frames; all authority-bearing variants have `committed=true` because the exact value must already exist in durable supervisor state before delivery.

Every payload is strict and bounded. The generated fixture corpus contains, for each variant, one valid frame and atomic empty-payload, missing-required-field, extra-field and wrong-direction mutants. Broker call ordinals are required only on the three broker variants and null otherwise. Every received frame is also checked against `rlm_workbench_attempt_authority`; a schema-valid frame from a stale attempt, fence, owner generation, workspace generation/revision or rebind token is rejected before semantic handling.

## 11. Snapshot, event and result closure

`RlmWorkbenchSnapshot` is the disconnect/reconnect read model. It contains:

- exact operation and workbench revision;
- workbench phase plus legacy projection;
- exact workspace generation/revision/checkpoint binding;
- bounded ticket references;
- exactly one terminal result or failure when terminal;
- explicit certainty.

Workbench event payloads are discriminated and carry event ID, cursor, workbench revision and commit status. Provisional events from an interrupted cell are never projected as committed and repeated event IDs are deduplicated.

`RlmWorkbenchResult` is valid only when output passes its admitted JSON contract, all required children are terminal, all named artifacts are committed by the finalization manifest, cumulative usage is exact, and workspace disposition is complete.

## 12. Artifact paths

`logical_name` is a relative POSIX-style path. Additional validators reject:

- empty or `.`/`..` components;
- leading `/`;
- backslash;
- NUL;
- duplicate normalized names;
- names not in the completion contract.

Artifact content is staged, never published directly from the worker. `ArtifactBinding` preserves logical name, role, operation, workspace generation and cell identity. Visibility is governed by the coordinator rules in `LIFECYCLE.md`.

## 13. JSON contract validation

The generated `RlmDirective` document is the sole runtime-owned planner schema for initial, correction, recovery and finalizer calls. Its fixed version and canonical digest are published by workbench capability output; caller job input has no planner-schema field and any attempted override is rejected as an extra property. The exact same schema bytes are embedded in each planner `model.request` response contract. Final output separately binds the caller-selected completion schema digest at admission. Validation occurs:

1. before a planner directive can mutate a workspace;
2. before a caller observation becomes a model receipt;
3. before a terminal result can succeed.

Invalid planner output may consume one bounded correction call. Invalid terminal output cannot become success. Remote references, parser ambiguity or cross-validator disagreement are terminal certain contract failures.

## 14. Error union

Every new tool returns exactly one of:

- its success schema;
- `aar.envelope.v1` `Failure`, with a closed category/code, a 1–512 character public message, retryability, certainty, optional operation reference, and at most 32 bounded scalar detail pairs.

The closed codes are:

`INVALID_ARGUMENT`, `CONTEXT_INVALID`, `CAPABILITY_UNAVAILABLE`, `GRANT_DENIED`, `BUDGET_EXCEEDED`, `CONFLICT`, `NOT_FOUND`, `ROUTE_UNAVAILABLE`, `CALLER_WORK_CONFLICT`, `CALLER_WORK_OUTCOME_UNKNOWN`, `WORKSPACE_FAILED`, `WORKER_LOST`, `RECOVERY_PLANNER_FAILED`, `ARTIFACT_PUBLICATION_FAILED`, `CANCELLATION_INDETERMINATE`, `DEADLINE_EXCEEDED`, `RECONCILIATION_REQUIRED`, and `INTERNAL_ERROR`.

Internal traces, credentials, local paths and provider secrets are not exposed in public messages or detail values. Integer and non-integer number branches are disjoint so Draft 2020-12 `oneOf` does not reject integers by double match.

## 16. Compatibility freeze

The released baseline discriminator is `aar.rlm.v1`, not `aar.rlm-job.v1`. Required compatibility evidence binds exact baseline schema/fixture/tool-surface/lifecycle digests.

- `aar_rlm_execute` v1 remains byte- and behavior-compatible;
- frozen v1 broker registry rows remain exact;
- frozen operation state and continuity responses remain exact;
- public caller-delegated plugin v1 bytes and lifecycle remain exact;

## 17. Candidate and evidence claims

The normative acceptance matrix has no mutable pass status. Candidate results are separate and validate against `aar-acceptance-evidence-v1.schema.json`.

Every candidate contains exactly one source archive and one `SourceManifest`. The manifest is file-bound, self-digested, clean-only, and binds candidate ID, source commit, archive digest/size and a canonical sorted inventory of regular files. Validation reads the archive without extracting it, rejects path escape and non-regular members, recomputes every file digest/size/executable bit, and recomputes `source_tree_digest` from the exact inventory. Exactly one `WheelBuildManifest` then binds its own bytes and semantic digest to that source manifest, commit, tree, archive, build command and exact wheel digest. A second source archive, dirty manifest, changed commit/tree/archive, changed source-manifest bytes or wheel/source mismatch fails closed.

Every evidence item binds exactly one `EnvironmentManifest`, test/probe bundle, `FixtureBundleManifest` and stdout file by path, size and SHA-256. The environment manifest binds candidate ID, source commit, target package, tool-surface digest, Python/platform/architecture, registry schema v6, runtime generation and command-environment digest. A fixture bundle contains at least one file entry and revalidates each entry's relative path, size and digest. A `SemanticReceiptDocument` is a schema-validated envelope whose content kind and candidate ID must match its outer receipt binding; digest-only or kind-mismatched shells fail.

Evidence v1 admits exactly one authoritative item for each `(acceptance_id, fault_case_id-or-null)` obligation and requires globally unique `evidence_id` values. Duplicate items and pass/fail conflict pairs are invalid rather than aggregated optimistically. V1 defines no implicit timestamp ordering or supersession; any future rerun/supersession feature requires a new signed contract with explicit predecessor identity.

Each reviewer signature is Ed25519 over canonical JSON `{schema_version, candidate_manifest_digest, evidence_item}`, where `evidence_item` omits only `review_signature` and `review_signature_digest`. Results publish the raw 32-byte public key through `ReviewKeyBinding`, but `validate_sdd.py --results` accepts it only when an out-of-band `--review-trust` store names the same reviewer principal/key ID and public-key SHA-256. A results bundle cannot nominate its own trust root. The signature file is exactly 64 bytes; its file binding is checked before cryptographic verification, so rebound hashes cannot legitimize a modified item or signature.

All six published schemas are checked against the Draft 2020-12 meta-schema. Negative fixtures are atomic pairs: the declared valid base must validate, the invalid fixture must fail, and applying the one declared JSON-pointer mutation to the valid base must reproduce the invalid bytes semantically.

A candidate is `implementation_verified` only when every required T0-T3 row and fault case has accepted, hash-bound evidence against one candidate manifest. It is `live_qualified` only after the separately authorized T4 rows also pass against that same candidate or an explicitly derived installation manifest.

Without T4 authorization the only honest status is `implementation_verified`; live qualification remains pending. Structural validation is never a product verification verdict.
